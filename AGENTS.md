# AGENTS.md

digestvo is a Bridgetown (Ruby) static site — a digested newsletter. Pinned versions: Bridgetown `~> 2.2.2`, Ruby per `.ruby-version` (4.0.7), Node >= 22.

## Commands

```sh
bundle install && npm install   # first-time setup
bin/bridgetown start            # dev server on :4000; runs esbuild watch + Bridgetown watch + live reload
rake deploy                     # clean + frontend:build + build  → output/
bin/bridgetown frontend:build   # bundle frontend only (minified)
bin/bridgetown frontend:dev     # esbuild watch only (not needed alongside `start`)
bin/bridgetown build --watch    # rebuild site on change, no server
bin/bridgetown console          # IRB with site loaded
```

- **Build order matters.** `bin/bridgetown build` on its own does *not* run esbuild, so it prints `esbuild: The esbuild manifest could not be found` and every `asset_path` in `_head.erb` breaks. Always `rake deploy` (or `frontend:build` first).
- **Verification is the build.** There is no test suite, linter, or formatter. `rake deploy` succeeding is the check. Do not invent `npm test` / `rake spec` / rubocop invocations.
- `rake test` is *not* a test suite — it only rebuilds the site with `BRIDGETOWN_ENV=test`.
- Production serving: `bundle exec falcon host config/falcon.rb`. `Rakefile`'s default task is `deploy`.

## Deployment

GitHub Pages at **https://digestvo.ezcurdia.dev** (custom domain), deployed by `.github/workflows/deploy.yml` on every push to `main` (and manual `workflow_dispatch`).

- CI runs `bundle exec rake deploy` with `BRIDGETOWN_ENV=production`, so **all assets are precompiled on deploy** — esbuild/PostCSS/Tailwind run and hashed filenames are baked in. Nothing under `output/` is ever committed.
- `upload-pages-artifact` ships `./output`, then `deploy-pages@v4` publishes it (Pages source must be **GitHub Actions**).
- `url` and `base_path` are set in `config/initializers.rb` and overridable via `BRIDGETOWN_URL` / `BRIDGETOWN_BASE_PATH`. Because the site is on a custom domain, `base_path` is `/` and links are plain root-relative.
- `src/CNAME` is copied verbatim to `output/CNAME`. The custom domain must also be registered under **Settings → Pages** in the repo, and DNS pointed at GitHub Pages.

## Architecture

- Content lives in `src/` (`_posts/`, `_components/`, `_layouts/`, `_partials/`, `_data/`) and is built to `output/`. Autogenerated dirs (`.bridgetown-cache/`, `output/`) are gitignored — don't edit or commit them.
- **Template engine is ERB, not Liquid** (`config/initializers.rb`). Markdown is kramdown, so `{:style="..."}` IAL attributes work in `.md` files even though ERB is used for `.erb`.
- Custom Ruby goes in `plugins/`: `plugins/site_builder.rb` is loaded automatically, and builders subclass `SiteBuilder` in `plugins/builders/`. This is the place for newsletter content generation/ingestion logic.
- `config/initializers.rb` is **not** hot-reloaded by `bin/bridgetown start` — restart after editing it.
- No SSR / Roda routes are enabled. `server/roda_app.rb` is just the dev-server plumbing; the sample route stays `.rb.sample`.
- Site title/description/email live in `src/_data/site_metadata.yml`, still holding scaffold placeholder values.

## Frontend / CSS pipeline

- Single esbuild entrypoint: `frontend/javascript/index.js`, which imports the two CSS files and `$components/**/*.{js,jsx,js.rb,css}`.
- esbuild emits hashed assets to `output/_bridgetown/static/` and writes the lookup manifest to `.bridgetown-cache/frontend-bundling/manifest.json`. Templates resolve assets through `asset_path :css` / `asset_path :js` (see `src/_partials/_head.erb`) — never hardcode a hashed filename.
- Path aliases `$styles/`, `$javascript/`, `$components/` are declared in `jsconfig.json` and handled by esbuild's glob plugin.
- CSS is processed by **PostCSS**, configured in `postcss.config.js` (@tailwindcss/postcss, postcss-preset-env with autoprefixer, postcss-flexbugs-fixes). Any new CSS tool must be registered there or it will not run. `@tailwindcss/postcss` must stay **first** in that list so Tailwind expands its directives before the compat passes rewrite its output.
- Bridgetown force-prepends its own `postcss-import` ahead of everything in `postcss.config.js` (see `importPostCssPlugin` in `config/esbuild.defaults.js`). The plugin order actually used is `[postcss-import, ...postcss.config.js plugins]` and cannot be reordered from this repo.
- **`config/esbuild.defaults.js` is Bridgetown-managed — do not edit it.** Put overrides in `esbuild.config.js`; `bin/bridgetown esbuild update` overwrites the defaults file.
- Sass is optional: `npm i -D sass` enables `.scss`/`.sass` handling in the bundler.
- npm 11 gates dependency install scripts, so esbuild's `postinstall` is skipped. That is fine — the platform binary ships in `@esbuild/<platform>`. Don't add an `allowScripts` entry unless something actually breaks.

### Tailwind

Tailwind CSS v4 is installed and wired into the PostCSS chain — there is no parallel build step. `frontend/styles/index.css` starts with:

```css
@import "tailwindcss" source(none);

@source "../../src/**/*.erb";
@source "../../src/**/*.md";
@source "../../src/_components/**/*.rb";
@source "../../frontend/**/*.js";
@source "../../plugins/**/*.rb";
```

- `source(none)` disables Tailwind's automatic content detection (which would otherwise scan the whole repo, lockfiles included). **When you add a new kind of file that contains classes — a new extension, a directory outside those globs — add a matching `@source` line**, otherwise its classes will be silently missing from the build.
- `@source` paths are relative to `frontend/styles/index.css`.
- The former `:root` variables are now `@theme static` tokens in the `--color-*` namespace, so both hand-written CSS and utility classes can use them: `--color-body-background`, `--color-body-color`, `--color-heading-color`, `--color-action-contrast`, `--color-panel-background`, `--color-surface-background`, `--color-border-color`, `--color-code-background`, `--color-code-color` → `bg-action-color`, `text-body-color`, etc. Add new tokens in the same block. Note `--color-panel-shadow` and `--color-neon-alt` were **removed** — the flat theme has no shadows and only one accent hue. **Keep the `static` keyword**: plain `@theme` tree-shakes variables no generated utility mentions, and since almost every token is referenced only from hand-written CSS, that silently drops them — a `var()` for a missing token fails at computed-value time and the declaration just inherits (no error, wrong color).
- **Dark mode is a `light-dark()` pair per token, not a `dark:` variant and not a media query.** Each `--color-*` token holds `light-dark(<light>, <dark>)` in `@theme`, and `html` carries `color-scheme: light dark` — the device picks the scheme, and everything referencing `var(--color-*)` (utilities included) flips with zero markup changes. **When you add a color token, give it both values in the same declaration**, or the missing side will inherit the wrong color. The footer's edition link can override the device via `:root[data-theme="light"|"dark"] { color-scheme: … }`; a tiny inline script in `src/_partials/_head.erb` restores the reader's stored choice from `localStorage` before first paint, and `frontend/javascript/index.js` toggles it (see Conventions).
- Token pairs in use: `--color-action-contrast` is the text color *on* an action-colored surface, so the CTA button passes AA in both schemes. `--color-code-*` is the code-block text pair; the block's *ground* is deliberately the same as the page, with a hairline border doing the delimiting.
- The theme is a **flat newspaper with one neon accent**: warm newsprint ground in light mode, near-black in dark, serif reading text, sans meta, hairline and double rules. The flat/neon part is a deliberate reversal of an earlier purple/violet neon attempt that read as too flashy. Rules to preserve:
  - **One ground.** `--color-body-background`, `--color-panel-background`, `--color-surface-background` and `--color-code-background` are all the same value in both schemes. Do not give `main` or a card its own fill; `main` has no shadow, border or radius either, so it is indistinguishable from the page. Post lists therefore have no card chrome — the bold title and muted date carry the hierarchy.
  - **One accent, used only on highlights**: links, the active nav item, headline hover on the index, focus rings, and the logo mark. Kickers, dates and section labels stay muted. `--color-action-color` is a neon orange (the morning-coffee association) — `#ff8c1a` on the dark ground, `#b34700` in light mode because raw neon orange is ~2:1 on white.
  - **One glow in the whole site, dark mode only**: a single wide `filter: drop-shadow()` on `.brand__mark` (10px blur, accent at 40% via `color-mix`), whose color is a `light-dark(transparent, …)` pair inside the declaration. On the light ground the same bloom reads as a grey smudge. Do not add glows to headings, wordmark or panels.
  - No purple/violet anywhere, and no gradients on rules or borders. Rules are flat `--color-border-color` hairlines, plus `3px double` under the masthead strip and over the footer, and a 2px heading-color rule under each edition date.
  - **One column for every page.** `main` stays full-bleed with a `clamp()` gutter; `src/_layouts/default.erb` wraps every page in `.column` (`--container-column`, 44rem ≈ 70 characters). The masthead and footer reuse that width so every edge lines up. Don't add per-page widths or put a `max-width` on `main`.
  - **Every page opens the same way.** Posts use `src/_layouts/post.erb` and everything else (About, Stories, 404, 500) uses `src/_layouts/page.erb`, both with the `.article__header` block: kicker, serif title, italic standfirst from `summary`, rule. The kicker comes from `tags` on a post; pages have none and open on the title alone. Page bodies get `.prose`; set `prose: false` when the body is a component instead of running text.
  - **`h2` inside `.prose` is a section label, not a headline.** `frontend/styles/index.css` sets it as small letter-spaced sans caps on a 2px heading-color rule — the same treatment `.edition__date` gives each day's stories on the front page — so the About page and the index share one voice. Only the About page uses it today; posts open under the layout's own "The discussion" label, outside `.prose`. Keep `h3` and below as serif headings.
  - **Typography split.** Newsreader Variable (`--font-serif`, self-hosted via `@fontsource-variable/newsreader`) for headlines and body; system sans (`--font-meta`) for dates, labels, nav and source links, uppercase and letter-spaced where it is a label. Body is 1.1875rem / 1.6.
  - **Source marks live in one component.** `src/_components/shared/source_links.erb` turns `source_url`, `hn_url` and `lobsters_url` into the "Read the original", Hacker News and Lobsters links. Posts never carry markup; the digest skill's `references/post-template.md` documents the front matter.
  - Code blocks are the one exception to the single-accent rule: `frontend/styles/syntax-highlighting.css` keeps a full-hue neon syntax palette, one `light-dark()` pair per class, because a spectrum reads as information there rather than decoration.
- The brand wordmark is **Alfa Slab One**, a single-weight (400) heavy slab cut, self-hosted via `@fontsource/alfa-slab-one/latin-400.css` in `frontend/javascript/index.js`. Asking for `font-weight: 900` fake-bolds it.
- Contrast is not decorative. Every token pairing must clear WCAG AA (4.5:1 body text, 3:1 for borders/UI). Check with a contrast function before committing a value — the scaffold's original `#d64045` link on `#f2f2f2` was only 4.01:1 and had to be darkened to `#c62f3c`. The dark border sits at `#636363` (3.3:1), the lightest neutral that still holds 3:1 on the near-black ground without looking like a bright outline.
- The hand-written defaults live in `@layer base`, **not unlayered**. Unlayered rules beat Tailwind's utilities layer, so an unlayered `a { text-decoration: underline }` would make `no-underline` silently do nothing. Keep new global element styles inside the existing `@layer base { … }` block.
- Preflight also lands in `@layer base`; within a layer, source order decides, so the block after the `@import` still overrides preflight.

## Conventions

- Post filenames must be `src/_posts/YYYY-MM-DD-slug.md`.
- The theme switch is the footer's `data-edition-toggle` button (plain text, "Night edition" ⇄ "Day edition"). It is rendered `hidden` and revealed by `frontend/javascript/index.js`, which also writes the choice to `localStorage["edition"]`; the inline script in `src/_partials/_head.erb` applies that key as `data-theme` on `<html>` before first paint. No stored key and no JavaScript both mean "follow the device" — don't add other entry points for scheme state.
- Keep new site-level settings in `config/initializers.rb`, reloadable metadata in `src/_data/site_metadata.yml`.
- `README.md` is still the Bridgetown scaffold README; it is not a reliable description of this project.
